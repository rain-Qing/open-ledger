## 1. 一句话定位

家庭成员或小团队成员（可扩展到多个真人账号）共用**一本账**：各记各的、数据互通、每条记录都能看出「归属 / 谁录的」。
管理员账号只做后台（建号、配 AI），不参与记账、不出现在任何候选里。

## 2. 页面与交互

底部四个 tab，全部单页切换，无路由跳转。

### 2.1 记一笔（默认页）

| 元素 | 行为 |
|---|---|
| 方向切换 | 支出 / 收入 / **退款 / 报销**。选「退款 / 报销」后再选一次类型：**退货退款 / 报销到账**；两者内部都是冲抵（`direction=refund`），靠 `offset_kind` 区分。切换会清空已选分类并重置冲抵候选 |
| 报销的分类 | **不给选**：有原单就继承原单分类，没有原单就落退款树兜底。所以「报销到账」模式下不显示分类卡片——露出来只会让人以为自己要选「购物退款」 |
| 报销的候选 | **只列标了「待报销」的支出**（`reimb_pending=1 AND reimbursed=0`），不按金额筛、不限 30 天窗口，按日期倒序全部列出；**可多选**。默认勾选**只在到账金额能覆盖全部候选时**才全选——金额没填或覆盖不了就先不选（否则用户还没说要报多少，系统已经替他圈了一堆，而提示还在说「先填到账金额」）。用户手动点过候选后，自动规则永久退出。卡片下方实时显示「已选 ¥x / 可冲抵 ¥y / 还差 ¥z」。仍按「归属」过滤，该人名下一条都没有时放宽到全部人 |
| 报销的差补 | 卡片排在「报销哪几笔支出」**下面**——先勾支出，差补自然就浮出来。到账金额里可能有公司按天包干的差补（你没垫过）：**默认自动填「到账 − 已选合计」**，勾选或金额一变就重算（算不出来时不填）；手动改过这一栏就不再被覆盖——出差几天他知道、系统不知道，提示里给一个「改回自动」。填好后选子类（出差补贴/餐补/其他补贴），提交后**拆成两条账**：冲抵记录（到账 − 差补）+ 收入记录（补贴·子类）。差补归属**跟原单**，不跟操作人。没认领的部分仍算无主冲抵 |
| AI 输入框 | 一句话识别（`glm-5.3-flash`，原生多模态），回填方向/分类/金额/备注/标记；未配 key 时置灰 |
| 拍照识图 | 输入框右侧相机键 → 选图/拍照，浏览器先压到长边 1600（JPEG 0.82）再上传；识别后缩略图留在原地可核对，下方显示「识别到：…」原文字样，**金额读错一眼能发现**；选完图自动开始识别，不用再点一次 |
| 金额 | 大号输入，Enter 直接保存；以「分」为单位提交 |
| 分类 | 两级胶囊，大类选中后展开子类；每个大类有固定底色 |
| 标记（仅支出） | 共同支出 / 待报销 / **待用券** / **旅行** 四个独立开关 |
| 冲抵哪一笔支出（仅退款） | 候选卡片，一行一笔，显示「日期 · 分类 · 备注」+「剩 ¥x」+ 匹配标签（同额 / 备注对得上 / 差 ¥x.xx）；默认预选最匹配的一条，可手动切「不冲抵」；底下有「搜更早的账单」 |
| 细节 | 日期、归属（胶囊，当前登录人置顶并默认选中）、备注 |
| 保存 | 「记这笔」，成功后清空金额/备注、保留分类与归属，方便连续记账；同时弹出**「已记上」结果抽屉**（见下） |

**关于 AI**（管理员在「设置」里配 Key 之后才有入口）

- 一个模型全包：`glm-5.3-flash` 是原生多模态，写一句话和拍张小票走同一个接口，不需要另配视觉模型
- 文字和识图**都带** `reasoning_effort=low`：文字约 1～2 秒，识图约 4～5 秒（2026-10-28 实测改的，见下）
- 识图 `max_tokens` 只给 600：压推理后输出只有 ~113 token，给多了反而是在鼓励它多想
- 识图的 prompt **只发 system 一份**，user 里只放「用户的补充说明」——两边都发白吃 539 个输入 token
- **备注只装「以后能想起这笔」的信息**（≤12 字）：买了什么 / 在哪 / 和谁 / 为什么，
  例如「食品袋」「和同事吃饭」「楼下超市」。不复述原句、不写金额日期、不写标记（待报销那些有专门的开关）。
  **前端不再兜底填原话**——模型没给备注就留空，原句只留在 AI 输入框里供回看
- AI 只生成草稿，**从不直接记账**：结果回填表单，用户确认后再点「记这笔」
- **语音输入：暂不做**（2026-10-28 定的）。`glm-5.3-flash` 的输入模态只有视频/图像/文本/文件，
  **不收音频**；要做得另接 `glm-asr-2512`，而它只收 `.wav`/`.mp3`、单段 ≤30 秒，
  浏览器录的 webm 得先转码。一句话记账本来三四秒就能打完，为省这一两秒不值这套复杂度。
  所以输入框文案写「**写**一句话」，不要写「说」——没有的能力别在界面上暗示。
- 分类越界兜底到该树第一项、标记只对支出生效、`reimb_pending` 与 `reimbursed` 互斥——脏值进不了库
- 每次调用（成功和失败）都写 `ai_log`，管理员在设置页能看近 7 天统计 + 最近 20 条，日志留 90 天

**AI 实测基线**（2026-10-27 上线当天，用真 Key 跑的，后续调 prompt 拿这个当对照）

| 场景 | 耗时 | token | 结论 |
|---|---|---|---|
| 文字一句话 | 2.2s | 入 42 / 出 34（推理 20） | `reasoning_effort=low` 确实生效（推理只有 20） |
| 识图 | 6.6s | 入 372 / 出 194（推理 163） | **带图时 `json_object` 可用**，返回纯 JSON 无 markdown 包裹；不压推理时推理量 163 |

空白测试图返回「未检测到任何文字」而不是瞎编一个金额——**视觉请求是真在看着图说话**，
这一点对「金额读错要能发现」的设计很关键。

**识图 A/B 实测（2026-10-28，两张真实账单截图，服务器上跑，与生产同网络出口）**

同一张图、同一条生产 prompt，只改分辨率与 `reasoning_effort`：

| 变体 | 耗时 | 入 token | 出 token（推理） | 金额 | 分类 |
|---|---|---|---|---|---|
| 1600 + **不压**推理（改前的线上行为） | **12.1s** | 2617 | 572（**410**） | ✓ 258.00 | 娱乐/游戏 |
| 1600 + 压推理 | **4.4s** | 2617 | 113（0） | ✓ 258.00 | 娱乐/其他 |
| 1024 + 压推理 | 4.2s | 1738 | 115（0） | ✓ 258.00 | 购物/其他 |
| 800 + 压推理 | 4.2s | 1486 | 115（0） | ✓ 258.00 | 购物/其他 |
| 1600 + 压推理 + prompt 去重 | 4.0s | **2078** | 108（0） | ✓ 258.00 | 娱乐/其他 |

第二张（微信 6.00）三档金额全对，分类从 餐饮/其他 掉到 其他支出/其他。

**三条结论，别再翻案：**

1. **压图几乎没用。** 1600 → 800 输入 token 降 43%（2617 → 1486），耗时只从 4.4 变 4.2 秒，在噪声里。
   图只喂 prefill，而 prefill 只占两成时间。省的是成本，不是时间。
2. **不压推理才是慢的根因。** 410 个推理 token 换 12.1 秒；压了是 0 个推理 token、4.4 秒。
   线上那次 26 秒正是「不压 + `max_tokens` 打满 1200 被截断」，**不是图太大**。
3. **不是零成本：分类会退化。** 不压时给「娱乐/游戏」（小黑盒是游戏平台，对），压了只给「娱乐/其他」。
   但**金额——唯一会毁账的字段——四档全对**。分类错了点一下胶囊改掉，两秒；等 8 秒是纯亏。这个交易成立，
   所以「识图不压推理、压了容易看错金额」这句话**被实测证伪，已删**。

日志本身没问题：成功失败都记、token 与耗时都在，就是靠这张表才定位到上面这些。

**关于键盘**：只有**用户自己点「金额」输入框**才会弹键盘。进入记一笔、切换方向 / 分类 / 标记 / 归属、
**以及保存成功之后**，一律不聚焦任何输入框（重渲染也不会把焦点塞回金额框）。
这一条是移动端的硬要求——手机上键盘一弹就把二级分类整个盖住，用户得反复手动收起。
代码里 `renderAdd()` 结尾刻意没有 `amt.focus()`，别「为了连续记账」再加回去。

**关于金额输入**：只接受数字和一个小数点，最多两位小数。**输入时就清洗**（全角数字、中文句号自动转半角，
其它字符直接吞掉），所以框里看到的就是最终会记下的数；提交前再严格校验一遍：空或全 0 提示
「请输入金额」，超过上限提示「单笔金额不能超过 100 万元」。

这条别退回去用 `parseFloat`：它会把「12abc」读成 12、「1e3」读成 1000、「1,000」读成 **1**，
错得毫无痕迹。记一笔、编辑记录、退款、借款、筛选金额区间五处输入框共用
`cleanAmount()` / `parseAmount()`，`AMOUNT_MAX_CENTS` 与后端 `_create_tx` 的上限（100 万元）一致。
后端接的是整数分，用 `int()` 严格转换，前端传脏值会被 400 拒绝（有用例锁着）。

**关于「已报销」**：不在记账页，也不能手填。它只在**记一笔到账**时由系统置位（明细行的「到账」按钮，
或手动记一条「退款 / 报销」并选上原单）——到账会同时冲减支出，标记和金额才是一回事。
编辑弹层里只在已有到账记录时显示一个灰掉的「已报销（有到账记录）」，没有记录时这一项完全不出现。

**关于「已记上」结果抽屉（2026-10-29，当晚改版）**

保存成功后弹出一张**底部抽屉**：`✓ 已记上这笔支出 / −¥16.79 / 支出 · 交通⁄打车 · 日期 · 归属`，
带备注行和标记标签（共同支出、待报销…），底部三个动作：

| 动作 | 做什么 |
|---|---|
| 记错了（左下，文字链） | `DELETE /api/tx/{id}` 撤掉这笔，并把金额和备注**放回表单**，改完直接重记；报销到账会连附带的那条差补收入一起删 |
| 再记一笔（右，描边） | 关掉抽屉、滚到金额框并聚焦，分类/归属/日期都留着 |
| 记完了（最右，实底） | 回页面顶部。表单已在提交成功时清空，那里就是新一笔的起点 |

右上还有 ×，点遮罩空白处也算结束——这两条是给熟练用户的快路径，**不出现在界面上**：
把它写成一行「点空白处关闭」的说明，等于承认交互没做好，还白占一行地方。
重复提交被拦下（响应带 `duplicate`）时**不显示「记错了」**：那一条是之前就存在的，撤它容易误伤。

为什么不再用页顶那张卡：卡片在文档流里，而「记这笔」在页面最末尾——提交时视口停在底部，
卡片渲染在视口之外，等于没有提示。**提示只要待在文档流里，可见性就取决于手指停在哪**，
模态与滚动位置无关，这才是「已记上」该有的形态。

**提交中的遮罩**：点「记这笔」后 **350ms** 才浮出全屏遮罩（`正在记…`）。本地请求常常 300~800ms
就回来，立即浮出只会闪一下、比不闪更让人不安。2.5 秒文案变「网络有点慢，还在等…」，
6 秒放出「先看看明细」——**只解锁界面，请求不中断**，真落库了回执照样弹出来。
遮罩**不负责防重**（那是 `state.saving` 加 `client_token` 唯一索引的事），它只负责让人知道在忙。

**关于重复记账：前后端各一道（2026-10-29）**

那三条重复的根因不是网络，是记账这条写路径**前后端都没有防重**：双击、断网重发、
结果未知时再点一次，每次都会真真切切落一条。

| 层 | 做法 |
|---|---|
| 前端·锁 | `state.saving` 在途锁 + 按钮变「保存中…」并 disable，直到这次请求有确定结果 |
| 前端·键 | 每次提交带 `client_token`（`crypto.randomUUID()`，老 WebView 兜底时间戳+随机数），**落账成功后换新的** |
| 前端·重发 | 断网/切网（`api()` 打 `network` 标记）时用**同一个 token** 自动重发一次：第一次若已落库，这次被服务端当重复拦下，回执照样给确定答案 |
| 后端 | `transactions.client_token` + `WHERE client_token IS NOT NULL` 的唯一索引；先查后插，撞索引再查一次，都返回原 id 并带 `duplicate: true` |

**幂等键标识的是「这一次提交动作」，不是这笔账的内容**——这是整个设计的关键。
拿金额/日期/分类去判重才是错的。同一天两笔都是 16.79 的打车，是两个不同的 token，
照常各记一条；只有「同一次提交到达了两次」（双击、重发）才会复用一个 token。
`tests/ledger_suite.py` 的 `T 幂等提交` 分组专门守着这条边界（含真并发两线程、连备注都空的两笔）。

服务端不做强制：老客户端不带 `client_token` 照样能记（`client_token IS NULL`，不受唯一索引约束）。
内部生成的记录（差补收入、冲抵分配）也不带键；报销到账的键只挂在**冲抵记录**那条主记录上——
两行带同一个键会直接撞唯一索引，反而把正常记账拦下来。

「到账」按钮同理：token 按按钮实例生成（`btn.dataset.token`），同一个按钮连点只会落一条，
列表刷新后按钮重画、token 自然换新。

**其余写按钮（保存、编辑、冲抵分配、退款、分类保存）走 `withBusy()`（2026-10-30）**

计一笔那条路有自己完整的三层防重，别的按钮没有：连点两下就真发两条（记退款最危险，
两条各自都「不超过剩余可退」，于是一笔钱退成两笔）。现在统一套一层在途锁——按下即 disable
并把按钮文字换成「保存中…」，落定后（无论成功、失败、用户取消）在 `finally` 里复位。

**请求 15 秒必断（2026-10-30）**：`api()` 用 `AbortController` 计时，超时走和断网同一条
「结果未知」分支（「网络中断，这笔可能已经到账——先刷新看一眼再决定」），**不谎报失败**。
没有这道闸时，「连上了但不回数据」会让 `await` 永不落定、按钮永远停在「保存中…」，
之后每次点击都被锁静默吞掉——这是最难查的一类故障。`window.__API_TIMEOUT__` 可临时改这个值。

**日期必填（2026-10-30）**：建账和编辑都在提交前拦空日期（「选个日期」），不发请求。
以前编辑把日期清空会送一个空串给后端，那笔账直接从月度视图里消失。

### 2.2 明细

- 按日期分组，组头显示当日合计（有冲抵的那几天写「净支出」）
- 顶部合计行：`N 笔 · 净流出 X · 原额支出 Y · 收入 Z · 退款 W · 报销 V`；一笔冲抵都没有时退化成 `N 笔 · 支出 Y · 收入 Z`
  - **「净流出」排第一并加粗（2026-11-02）**：明细行显示的是冲抵后的净额，合计行却把原额合计顶在最前面，
    两边看起来像两个账本。现在宁可不叫「支出」——改成「原额支出」，让主数字与每行同一个口径。
  - **叫「净流出」不叫「净」（2026-10-30）**：这一行按**每笔记录的日期**归月，而统计页的「支出」按**原支出月**归月。
    跨月冲抵时两页每月必然差一笔，以前两处都叫「净/支出」，看账的人只会以为哪边算错了。
    改名之外还在合计行下面补一句「净流出 = 原额支出 − 退款 − 报销，按记录日期归月」——**差异是口径不同，不是 bug**。
  - **合计行下面第二句是必读的（2026-11-02）**：`每行的大数字已是冲抵后的净额，退款/报销另占一行——别把两行相加`。
    因为冲抵记录没有降级、仍显示自己的金额，把「原单净额」和「冲抵记录金额」相加必然重复扣一次；
    真正能相加的只有导出 CSV 的「净额」列（已分配出去的冲抵行记 0）。
  - **每一段自己不断行，段与段之间可换行**（`.sum-line` 是 `flex-wrap`）
  - 这不是排版偏好：整段 nowrap 时，一个月几万块的金额 + 退款 + 报销 + 净额能把这行撑到 500px，比手机视口还宽。
    页面一旦有横向溢出，iOS / WebView 会把**布局视口一起撑宽**，而所有 `position:fixed` 的层（编辑弹层、筛选面板、冲账详情、底栏）
    都按视口宽度渲染，于是右侧被切掉——2026-10-29 线上「所有二级窗口显示不全」就是这个原因（vivo/Android WebView 不复现，因为那边 fixed 层不随布局视口变宽）
  - 兜底：`html,body{overflow-x:clip}`。用 `clip` 而不是 `hidden`——`hidden` 会造出滚动容器（并让吸顶头失效），`clip` 只裁掉不产生可滚动区域，也就不会撑宽视口
- 筛选按钮 + 已选条件胶囊（可单个 ✕ / 全部清除）
- **筛选面板第一屏就是搜索**：关键词框（金额 / 备注 / 归属，空格分隔多个词）→ 日期区间胶囊 → 方向 / 标记 / 归属 / 大类 / 金额区间
  - 关键词空格分隔＝多个词都要命中；命中处黄色高亮（金额只在整串相等时高亮，搜「25」不会点亮「¥125.00」里的 25）
  - **输入数字时原额和净额都认**（2026-11-02）：退了 900 的 1000 元那笔，搜 `1000`（账单上的数）和搜 `100`（屏幕上显示的数）都能找到。
    只认原额的话，屏幕上的数字搜不到，等于「看得见、找不着」
  - 日期默认「跟随月份」，输入关键词会自动切到「近12月」并在胶囊上高亮；用户自己选过区间就不再自动改
  - **「金额区间」按原额筛，不按净额**（2026-11-02）：用这个框的场景是「我记得那笔花了一千多」，人记的是付款额。
    标签直接写「金额区间（原额，元）」，面板里再加一句说明——显示净额、排序净额、筛选原额，三个口径不一样，必须写在脸上
- **标记可以反选（2026-10-29）**：同一个胶囊点一下＝只看这种（绿），再点＝**排除**这种（红底 ✕），第三下取消
  - 多种「只要」之间是**或**（勾「待报销 + 已报销」＝两种都要，否则两项不可能同时成立，结果恒空）
  - 多种「排除」之间是**或再取反**（任一种命中就排除），可以和「只要」叠加：
    例「近30天 + 支出 + 旅行，但排除已报销、有退款」→ `mark=travel&exclude=reimb,refunded`
  - 排除单独成排会变成 13 枚胶囊，反而更难找；三态把两件事塞进一行，代价是得靠一行提示教会（面板里就写着）
  - 筛完顶部胶囊分红绿两种：绿＝要、红「排除 …」＝不要，点各自 ✕ 只清那一种
- 排序按钮：`日期 新→旧`（默认）/ `日期 旧→新` / `净额 高→低` / `净额 低→高`，**与筛选叠加**（先筛后排，互不覆盖）
  - **原来是「金额」，2026-11-02 起改成「净额」，且带符号**：支出取 `原额 − 已分配冲抵`，退款/收入取负值。
    于是「高→低」里退完的沉底、「低→高」里退款排最前——退款对流出是负贡献，按原额排会让全额退完的那笔继续占榜首。
    服务端的 `TX_ORDERS` 用同一个 SQL 片段 `NET_OUT_SQL`，桶只有四个键，外部字符串拼不进 SQL
- **导出按钮（2026-10-30）**：把当前筛选结果下载成 CSV，Excel / WPS / Numbers 双击就能开
  - 和列表**共用同一个 `filterQuery()`**，服务端也共用同一个 `tx_filter()`——两边各写一套过滤是这类功能最常见的错法：
    用户勾了「待报销」导出，文件里却混着别的，比没有导出更糟。所以验收只认一条：**导出行数 = 页面上的 `summary.count`**
  - 带 UTF-8 BOM、CRLF 行尾、金额写 `123.45`（两位小数、不带 `¥`、不带千位逗号）——不加 BOM 的 CSV 在中文 Windows 上双击就是乱码，
    而「打开是乱码」会被当成文件坏了直接删掉；带 `¥` 或千位逗号则会被 Excel 认成文本，一列数字求不了和
  - 文件名 `ledger-2026-11.csv`，按 `month` 参数取；只认 `YYYY-MM` 这一种形状，其余一律叫 `all`（白名单比过滤省心，不用逐个字符担心响应头注入）
  - **与列表的唯一区别是不截断**：列表一次最多 500 行（页面也翻不动那么多），导出是「把这份筛选整份拿走」，截断就成了悄悄少数据
  - **两列金额（2026-11-02）**：`金额(元)` 是这笔记录原本的数，`净额(元)` 是**这一行计入净流出的金额**——
    支出 = 原额 − 已分配冲抵；退款/报销 = 已分给支出的部分记 **0**（那笔钱已经扣在原单上了，再记一次就是重复），
    只剩没分配出去的部分记负数；收入记负数。**整列 SUM 出来就是页头的净流出**，这是它唯一值得存在的理由。
    注意它与页面行里的大数字有一处刻意不同：页面上的退款行显示 `↩ 原额`（那是在说「这笔记录多少钱」），CSV 里那一行净额是 0
- 月份可以放开：从统计页点「待报销 / 待用券」跳进来时不再限当月，顶部的月份框换成「全部月份 · 按月查看」按钮
- 每行：**分类路径（一级 / 二级，只有二级加粗）** → 第二行「徽标 + 备注」→ 右侧快捷按钮 + 金额（金额下面一行小字是归属人）
  - **大数字是净额，原额退成小字（2026-11-02）**：有冲抵的行显示 `−5133.90`，下面 10.5px 的灰字写 `原 ¥7533.90`。
    理由是「这笔到底花了多少」才是看明细时要回答的问题，而统计页、金额排序、导出 CSV 早就是净值——只有明细还在用原额，
    一个页面两套口径。原额不删，是核对账单时还得对得上银行流水那个数
  - **净额 = 0 时写 `0.00`，不写 `−0.00`**（负零看着像算错了），整笔金额也用浅灰——全额冲抵是个正常状态，不该继续抢眼
  - **徽标把金额也带上**：`退 ¥2400.00` / `已报 ¥670.00`。原来「已报销」只有四个字不带金额，于是净额和原额差多少、
    为什么差，在列表里完全看不出来（2026-11-02 用户截图反馈的正是这个）。「已报销」无记录（历史遗留数据）时仍写纯文字
  - 标题是一级/二级的完整路径：一级用 11.5px 浅灰、二级加粗。只让二级重，整屏的重心才落在「午餐 / 买菜 / 早餐」这几个具体词上
  - 一级自己就是兜底大类（其他支出 / 其他收入）且二级也叫「其他」时，**只写一级**——「其他支出」比「其他支出 / 其他」有信息量，也还分得清钱是进来还是出去
  - 第二行只有一个槽位：**有备注就写备注，没备注就空着**（不再拿一级大类来填）。徽标（共同 / 待用券 / 待报销 / 已报销 / 已退）排在备注前面，不再挤在标题行
  - 退款行写「冲抵 MM-DD 原单一级 / 二级 [· 备注]」；报销冲抵的行写「**报销冲抵** MM-DD …」，标题固定是「退款 / 报销到账」——
    它的分类是从原单继承的，照原样写会让人以为今天真花了这笔钱。没有原单时写「无主退款 / 无主报销」
  - 平铺排序（按金额）时第二行最前面加日期，日期排在徽标之前
- **方向用整张卡的底色区分（2026-10-29）**：支出白卡、收入淡绿、退款/报销淡橙，左边缘一条 4px 竖条同色。
  只给少数派上色——一家一天十几笔支出，全上色只会发灰；彩色一出现就是「钱进来 / 退回来」，扫一眼就分得开。
  颜色不是唯一线索，金额前的 `− + ↩` 一直保留
  - 徽标因此统一改成**白底 + 描边 + 语义色文字**，放在淡绿/淡橙卡上不会和底色调混
  - 归属人只在**列表里出现不止一个人**时显示（金额下方小字）；按归属筛过之后整页都是同一个人，这一行自动省掉
- 快捷按钮按状态出现：
  - 待用券 → 「处理」（三个出口：用掉了 / 退掉了 / 过期作废）
  - 支出且还有剩余可退 → 「退」（直接发起一笔冲抵退款）
  - 待报销 → 「到账」（**生成一条报销冲抵记录**并冲减支出，不是改个标记；默认按剩余可冲抵全额，
    公司只报一部分时去编辑那条冲抵记录改金额，差额留作自付）

**报销的联动规则（2026-10-28 统一，别拆开改）**

状态只有**一个真相源**：那条「报销到账」冲抵记录。原单上的 `reimbursed` 只是它的影子，动记录就同步动它：

| 动作 | 联动结果 |
|---|---|
| 点「到账」/ 记一笔填报销到账 | 生成冲抵记录 + 原单 `reimbursed=1`、`reimb_pending=0` |
| 删掉那条「报销到账」记录 | 原单退回**待报销**（不是变成普通账单），「到账」按钮回来 |
| 编辑原单想关掉「已报销」 | **拒绝**，提示先删那条记录。有记录时开关直接置灰——不给两条路 |
| 报销金额 | **不算「已退」**：已退徽标只看退货金额，报销单列 `reimb_cents`；剩余可冲抵 = 原额 − 退货 − 报销 |
| 冲抵记录的归属/分类 | **全部继承原单**，不取填写人、不取表单选的值（冲抵记录是原单的影子） |
| 报销候选的「归属」 | 按选定归属人过滤；**该人名下一条可报的都没有时放宽到全部人**，并在候选下方注明（否则管理员这类名下无账单的账号永远看不到候选） |
| 报销 vs 退款候选 | **两条路，别合并**。退款是「一单一单退」，按「单笔剩余 ≥ 退款额」筛；报销是「一次到账摊多笔」，单笔金额天生小于到账额，套退款的规则会让 5 笔待报销一笔都不出现（2026-10-28 实测：填 5000 时推上来一笔没标记的 7533.90 还自动选中了）。所以报销不按金额筛、不预选单笔、不限窗口 |
| 差补为什么单开一条收入 | 冲抵是收回垫付（减支出），差补是公司白给的（增收入），性质不同。混在一条记录里，统计要把一条拆两半算，且「补贴」分类会被垫付收回的钱污染——那是年终看「今年补贴拿了多少」的地方。两条记录备注互相指认，流水对得上 |
- 点整行进编辑弹层
  - 方向下拉写「支出 / 收入 / **退款 / 报销**」——`refund` 一个方向装着退货退款和报销到账两种，靠 `offset_kind` 区分；
    冲抵来源那块也跟着说清是「冲抵」还是「报销冲抵」，无主时分「无主退款 / 无主报销」
  - **挂了原单的冲抵记录，方向 / 大类 / 子类三格是灰底只读**，右侧小标签写「退货退款 / 报销到账」「跟随原消费」，
    说明行里的「原单」链接可直接跳过去改（见 §5.5）。理由是服务端一律按原单覆盖这三个字段，
    给下拉就是「选了、保存了、没变化」
  - 「待报销 / 已报销」只在**支出**方向出现。标记只属于支出，在退款记录上显示这两个开关会让人以为能标记，
    实际保存时后端会把它们清 0——界面不该给这种空操作
  - **「已报销」不再是可点的开关（2026-10-30）**：没到账记录时它**根本不显示**；有记录时是一个
    灰掉的「已报销（有到账记录）」。它代表「钱已经收回来」，得有一条到账记录同时把金额冲掉，
    手点只会让标记说已报、净支出一分没减（R14）。要标记就去明细点「到账」或记一笔「退款 / 报销」。
  - **这笔有报销到账记录时，「待报销」也置灰**（虚线圆、半透明）。状态由那条记录决定，
    要撤回只有一条路：到明细里删掉那条「报销到账」，删了它原单自动回到待报销。
    接口层三面都拒：`reimbursed=true` 而无记录 → 400 `reimburse_requires_record`（建账、改账都拒），
    `reimb_pending=true` 或有记录时 `reimbursed=false` → 400「先删那条记录」。绕开界面也造不出矛盾状态
  - 说明块（浅黄底）摆在**开关上方**，标题「报销状态已锁定」，正文三段：
    **哪一笔**（已于 10-28 到账 ¥6.70）→ **为什么不能改**（状态以该记录为准）→ **怎么改**（删掉明细里的
    「报销到账」记录，删完恢复为待报销）。日期来自列表接口的 `reimb_date`（`MAX(tx_date)` 子查询），
    只给金额不给日期时用户还得自己去明细里翻是哪条

**排序与分组的配合**：选「日期」两种时保持按天分组（组头 + 当日合计，按**净额**求和；当天有冲抵就写「净支出」，
否则写「支出」），组顺序也跟着正序/倒序走；
选「净额」两种时会打散日期分组，列表平铺、每行第二行自己带日期（排在最前，先于徽标）——否则「组内按净额排」等于没排。
排序只改顺序，不改命中集合，顶部 summary 与筛选结果始终一致。

### 2.3 借款台账（明细页顶部）

借款**不进流水、不进任何统计**，只用来「别忘了谁还欠我钱」。入口是明细页顶部的一条提醒，翻明细就一定看得见，不占底栏。

- 折叠态：`借款` / `借出 ¥100,000.00 · 借入 ¥3,000.00 未结` / `2 笔 展开`
- 展开后是列表：对方 · 借出/借入 · 日期 · 备注，右侧剩余金额 + 「记还款」
- 底部「＋ 记一笔借款」，弹层里填方向 / 对方 / 金额 / 日期 / 谁借的 / 备注
- 编辑弹层里有「全部还清了」，一键把已还填成全额；已还 ≥ 借款额时自动标记结清，列表里变灰
- 没有未结清时也保留一条浅色入口，不至于找不到地方新增

**为什么不复用交易表**：借款不是收支。塞进流水意味着统计、筛选、分类饼图里处处要记得排除它，漏一处就静默算错；独立一张表则天然不进统计。

**代价**：借出的钱确实从银行卡出去了，所以「收入 − 支出」的结余会和银行卡余额对不上（借出那天差一笔，还回来那天又差回来）。这是换取「消费统计干净」的代价。

### 2.4 统计

按月查看，默认当月。

| 卡片 | 内容 |
|---|---|
| 本月收支 | 结余大字（正绿负红）；收入/净支出对比条；有退款时多一行「原支出 X，退款冲抵 −Y（另有本月无主退款 −Z），实付 N」 |
| 报销 | 待报销（**跨月累计**，净值）+ 本月已报销 |
| 待用券 | 买了还没用掉（**跨月累计**，净值）+ 笔数 |
| 共同支出 | 家庭公共开销（已扣退款） |
| 归属 | 本月净支出，扇形图 + 图例（金额/占比） |
| 支出分类 | 本月净支出，取前 8 个大类，扇形图；图下一行算式「分类合计 − 冲抵后为负 − 无主冲抵 = 支出」（见 §6.1 末） |

**每张卡片右侧的数字都能点**，点了直接跳到明细页并带上对应筛选，看完能接着做抵扣（「到账」/「处理」）：

| 点哪里 | 跳到明细的筛选 | 月份 |
|---|---|---|
| 待报销 | `mark=pending` | **放开限制（全部月份）**——跨月累计的指标跟着当月筛只会看到一小部分 |
| 本月已报销 | `mark=reimb` | 跟随所选月份 |
| 待用券 | `mark=voucher` | **放开限制（全部月份）** |
| 共同支出 | `mark=shared` | 跟随统计页所选月份 |

放开月份时，明细页顶部不显示空的月份框（原生控件会写成「----年-月」，像坏了），而是换成
「全部月份 · 按月查看」按钮，点它回到本月；「清除全部」也会一并把月份复原。

一处口径差异要知道：共同支出在统计里是**已扣退款**的净额，跳进明细看到的是每笔的**原始金额**
（退款挂在行上，显示为「退 ¥xx」徽标），所以明细的支出合计会比卡片上的数字大，差额就是已退的部分。

## 3. 数据模型

流水单表 `transactions`，配套 `users` / `sessions` / `settings`，外加一张**独立的** `loans`（借款台账，不进流水也不进统计）。

```sql
CREATE TABLE transactions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  tx_date      TEXT NOT NULL,          -- YYYY-MM-DD
  direction    TEXT NOT NULL,          -- expense / income / refund
  cat_parent   TEXT NOT NULL,          -- 大类
  category     TEXT NOT NULL,          -- 子类
  amount_cents INTEGER NOT NULL,       -- 金额，单位「分」，整数
  shared       INTEGER NOT NULL DEFAULT 0,   -- 共同支出（仅支出有效）
  reimbursed   INTEGER NOT NULL DEFAULT 0,   -- 已报销（仅支出有效；点「到账」后置 1）
  reimb_pending INTEGER NOT NULL DEFAULT 0,  -- 待报销（仅支出有效）
  pending_use  INTEGER NOT NULL DEFAULT 0,   -- 待用券（仅支出有效）
  travel       INTEGER NOT NULL DEFAULT 0,   -- 旅行（仅支出有效）
  parent_id    INTEGER REFERENCES transactions(id) ON DELETE SET NULL,  -- 冲抵的「主原单」，只用于列表显示
  offset_kind  TEXT NOT NULL DEFAULT 'refund',  -- 冲抵类型：refund 退货 / reimb 报销（仅 direction=refund 有意义）
  client_token TEXT,                   -- 幂等键（这次提交的随机标识，不是业务内容）；老数据/内部记录为 NULL
  owner_id     INTEGER NOT NULL REFERENCES users(id),   -- 这笔钱算谁的
  note         TEXT NOT NULL DEFAULT '',  -- 截断到 100 字
  created_by   INTEGER NOT NULL,        -- 谁录的
  created_at / updated_at TEXT NOT NULL
);
-- 幂等：只约束非空值，所以不带键的记录（老数据、差补收入、冲抵分配）可以有无数条
CREATE UNIQUE INDEX idx_tx_client_token ON transactions(client_token)
  WHERE client_token IS NOT NULL;
```

**金额归属在另一张表 `offset_links` 里，不在 `parent_id` 上**——一次报销可能对应好几张订单：

```sql
CREATE TABLE offset_links (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  offset_id    INTEGER NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,  -- 那次到账/退款
  parent_id    INTEGER NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,  -- 被冲抵的支出
  amount_cents INTEGER NOT NULL,        -- 这次分给它多少
  created_at   TEXT NOT NULL
);
```

规则：

- 一条冲抵的**分配合计 ≤ 它自己的金额**，差额算「未分配」，统计上按**无主**处理（算在到账当月）。
- 每笔支出的**被冲抵总额 ≤ 原额**（跨所有冲抵记录累计，`check_links` 里校验）。
- 没有分配 = 完全无主。`parent_id` 只是「主原单」（分配金额最大的那条），
  统计、额度、状态一律不看它——两处真相迟早打架，这个项目已经吃过一次亏。
- 删原单 / 删冲抵记录都靠外键 `CASCADE` 清分配表，再重算受影响原单的报销状态。

索引：`idx_tx_date`、`idx_tx_owner`、`idx_tx_pending`、`idx_tx_parent`、`idx_tx_pending_use`、`idx_tx_travel`；
分配表上 `idx_off_links_off`、`idx_off_links_parent`（统计每次都要按这两列聚合）。

借款另用一张表，**和流水完全隔离**，所以统计天然不受影响：

```sql
CREATE TABLE loans (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  direction     TEXT NOT NULL,     -- out 借出（别人欠我）/ in 借入（我欠别人）
  counterparty  TEXT NOT NULL,     -- 对方
  amount_cents  INTEGER NOT NULL,
  repaid_cents  INTEGER NOT NULL DEFAULT 0,
  loan_date     TEXT NOT NULL,
  note          TEXT NOT NULL DEFAULT '',
  owner_id      INTEGER NOT NULL REFERENCES users(id),  -- 谁借的
  settled_at    TEXT,              -- 还清时间，空了就是没还完
  created_by    INTEGER NOT NULL,
  created_at / updated_at TEXT NOT NULL
);
```

AI 调用日志单独一张表，跟流水无关，删了也不影响账目：

```sql
CREATE TABLE ai_log (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  ts                TEXT NOT NULL,
  kind              TEXT NOT NULL,            -- text 一句话 / image 拍照识图
  model             TEXT NOT NULL,
  user_id           INTEGER,
  input_brief       TEXT NOT NULL DEFAULT '', -- 只存前 120 字摘要，不整段留
  image_bytes       INTEGER NOT NULL DEFAULT 0,
  latency_ms        INTEGER NOT NULL DEFAULT 0,
  prompt_tokens     INTEGER NOT NULL DEFAULT 0,
  completion_tokens INTEGER NOT NULL DEFAULT 0,
  status            TEXT NOT NULL,            -- ok / error
  error             TEXT NOT NULL DEFAULT '',
  draft             TEXT NOT NULL DEFAULT ''  -- 当时返回的草稿 JSON
);
```

按 `ts` 建索引（`idx_ai_log_ts`）；每次写入顺手删 90 天前的记录，不另起 cron。

**几条硬约定**

1. 金额全部整数分，前后端都不碰浮点2. 退款不改原单金额，只新增一条 `direction='refund'` + `parent_id`
3. 退款状态**派生不冗余**：`refunded_cents = SUM(子退款金额)`，不存冗余字段，避免不一致
4. 迁移写在 `init_db()`，用 `PRAGMA table_info` 判存在后 `ALTER TABLE`，**重启即生效**，无需手工动库
5. `ON DELETE SET NULL`：删原单时退款变「无主」，不会被连带删除

## 4. 标记语义

| 标记 | 字段 | 含义 | 谁管 |
|---|---|---|---|
| 共同支出 | `shared` | 家庭公共开销，统计里单独汇总 | 记账时选 |
| 待报销 | `reimb_pending` | 自己先垫了，等公司/别人打钱 | 记账时选 |
| 已报销 | `reimbursed` | 钱已到账 | **只由到账记录置位**（`/api/tx/{id}/reimburse` 或记一笔报销到账）；手填一律 400 |
| 待用券 | `pending_use` | 团购/预付的券还没消费 | 记账时选，明细里「处理」 |
| 旅行 | `travel` | 把一个行程的吃住行串起来；分类仍按真实属性记，筛「旅行」看这趟总花费 | 记账时选 |
| 有退款 | 派生 | 存在子退款记录 | 自动 |

**互斥与清理规则**

- `reimb_pending` 与 `reimbursed` 互斥：新建时同传 → 待报销优先；编辑时**显式打开哪个就把另一个关掉**
- 方向不是「支出」时，**四个标记一律清空**（`shared` / `reimb_pending` / `pending_use` / `travel`），标记只属于支出
- 全额退完时自动清原单的 `reimb_pending` + `pending_use`（钱都没了，不必再垫/再用）
- 部分退款**不**清标记（还有钱在里面）

## 5. 退款与冲抵

### 5.1 模型

- 一对多：一笔支出可以挂多笔退款（100 买两个退一个 50 → 再退 50）
- 每条退款校验「金额 ≤ 剩余可退」，剩余 = 原金额 − 已有子退款合计
- 退款**继承**原单的分类与归属（钱回到谁那儿，就跟着原单的归属走）
- 但退款记录的 `created_by` 是实际操作人 → `/api/refunds` 同时返回 `owner_name`（算谁的）和 `created_name`（谁退的）

### 5.2 四种入口

| 入口 | 场景 | 行为 |
|---|---|---|
| 明细行「退」按钮 | 主路径，100% 准 | 直接带上 `parent_id`，金额预填剩余可退；类型固定为「退货退款」 |
| 明细行「到账」按钮（待报销的单才有） | 公司打款回来 | `POST /api/tx/{id}/reimburse`，金额按剩余可退，类型固定为「报销到账」 |
| 记一笔切「退款 / 报销」 | 手动补记 | 可再选「退货退款 / 报销到账」；走候选匹配（见 5.3），也可以不选原单记成无主 |
| 待用券「退掉了」 | 券没用成自动退款 | 先转退款流程，再冲抵 |

**四条入口录出来的账，明细上长得一样**——差别只由两件事决定，跟从哪儿录无关：

| 有没有挂原单 | 明细第一行 | 明细第二行 |
|---|---|---|
| 挂了 | 原消费的分类路径（如「娱乐 / **旅行**」） | `冲抵 09-19 娱乐 · 旅行 ¥380.00`（报销的写「报销冲抵」） |
| 没挂 | 退款树里的分类（如「退款 / **购物退款**」） | `无主退款（没有关联支出）`／`无主报销` |

底色与 `↩` 徽标两者一致。唯一实质差别在统计：挂了的按**原消费的分类**抵扣，没挂的只减少当月净支出、不进分类占比（见 5.4）。

### 5.3 候选匹配与预选

候选来源：`/api/refund-targets`，条件为「支出 + 近 30 天 + 还有剩余可退 + 剩余额度不小于退款额」，可按归属过滤。窗口取 30 天是因为实际使用中退款周期通常在 1~6 天，更早的原单走「搜更早的账单」。

三条通道，按强度排序，最多返回 8 条：

| 通道 | 含义 | 标记 |
|---|---|---|
| `same` | 剩余可退金额与退款金额完全相等 | 同额 |
| `kw` | 退款备注的关键词在原单备注里出现（覆盖「一单多件只退其中一件」） | 备注对得上 |
| `near` | 剩余额度比退款额多，且在容差内 | 差 X.XX |

容差 = `min(max(5 元, 退款额 × 50%), 200 元)`，只向上放宽（退款额不可能大于原单剩余可退，服务端会拒）。超出容差、且备注也对不上的支出不进候选——避免「退 15 元冒出一串 56 元」那种没法选的长列表。

**预选规则**：默认预选排序第一的候选，并在界面上标明「同额 / 备注对得上 / 差 X.XX」；只有 top1、top2 完全同分（同额两笔、同日同额）时才不预选，落回「不冲抵」。金额、归属人或备注一改，重新匹配并重新预选。

**搜更早的账单**：候选卡内展开的关键词/金额搜索，走 `/api/tx?direction=expense`，不受 30 天窗口限制，用来兜住跨月很久的原单。

### 5.4 无主退款 / 无主报销

匹配不上任何原单、或者到账了还没认领（未分配），都算「无主」：统计上减少**它发生当月**的净支出，
不影响任何分类占比。后续可以在编辑弹层的「冲抵分配」里认领到具体账单。

**冲抵分配（一条到账对多笔支出）**：公司一次打回 900，对应的可能是 700 + 200 两张单。点开一条冲抵记录 →
「冲抵分配」，二级弹窗里列出已分配的账单（日期 / 分类 / 原额 / 本次分多少 / 这笔最多还能分多少），
可以改金额、删掉、再添加一笔。顶部实时显示「本笔 / 已分配 / 未分配」。

- 每次保存是**整体替换**（一次请求内金额守恒成立），不是逐条调接口，不会出现「删了旧的还没加新的」的中间态。
- 分给多笔时，统计按**各自原单的分类**分别抵扣——这是关联表真正的意义。
- 明细行副标题写「报销冲抵 **3 笔支出**」，不点名某一单：一条记录只有一格标题，主题那格分类取的
  只是「分配额最大的那笔」，点名会让人以为整笔都冲在那一单上。点进去（或「冲抵分配」）能看到全部。
- **主原单 = 分配额最大的那笔**，明细标题的分类与归属都跟它。改完分配金额，主原单和标题分类会一起换
  （2026-10-29 之前只换 `parent_id`，标题还留着旧分类）。
- 摊在多笔上的冲抵，金额不能在编辑弹层里直接改（会把各笔的钱冲散）：那一格是灰的，去「冲抵分配」里调。
  接口也拒（`PATCH` 传新金额返回「请到冲抵分配里改金额」）。
- 原单的编辑弹层里也能看到它的**所有冲抵记录**（退货 + 报销，带类型），每条可删；删了状态自动回退。

### 5.5 编辑一条冲抵记录：方向和分类是灰的（2026-10-29）

挂了原单的退款 / 报销，编辑弹层里**方向、大类、子类三格都是灰底只读**，右侧小标签分别写
「退货退款 / 报销到账」和「跟随原消费」。没挂原单的无主退款仍是正常下拉，可自由选退款树里的分类。

为什么要锁：服务端 PATCH 一律按原单覆盖这三个字段（`_api_patch` 里 `parent, cat = orig[...]`）。
以前前端把它们做成可选下拉，用户改成「退款 / 购物退款」→ 点保存 → 弹「已保存」→ 实际一个字没变。
**这是唯一没有报错的失败路径**，只会让人以为自己手滑了。

- 说明文字里带一个「原单」链接：点它直接打开原单的编辑弹层（按原单所在月份捞一次，跨月也能跳）。分类要改就在那儿改。
- 或者先点「解除冲抵」：解绑后这条变成无主退款，分类回落到「退款 / 其他退款」，下拉恢复可选。
- 金额、日期、备注仍然可改；**归属不可改**（2026-10-30 起后端无条件按原单覆盖，见 §15）。
  归属只影响明细里写谁，统计一直按原消费的人抵扣——允许改会造出「明细算 A、统计按 B」两套账。
  前端同步改成只读展示（`归属人 · 跟随原账单`＋一行「要改归属，去原账单里改」），
  `owner_id` 也不再随请求发出去——留个能点的下拉只会让人以为点了有用。
- 接口侧保持宽容：显式传别的分类进来**不报错也不生效**。故意不返回 400——旧版前端（PWA 缓存着老 HTML）
  保存时会把整包字段带上，改成报错会让「只改个备注」也失败。

## 6. 统计口径

### 6.1 核心公式（归属月）

```
净支出 = 毛支出
       − 冲抵(分配回本月支出的部分，不论这笔到账发生在哪个月)
       − 未分配/无主冲抵(没认领的部分，算在它发生的月份)
```

- **「冲抵」按分配算，不按冲抵记录的总额算**：一条 900 的报销如果分给 700（其他支出）和 200（交通），
  就分别抵这两笔所在月的支出，不在同一个月里一次性减 900。

- 冲抵有两种：`offset_kind='refund'` 退货退款、`'reimb'` 报销到账。**统计上完全等价**，
  分开只为报表各说各的（「退款」卡不含报销，「报销到账」卡不含退款）。
- **报销为什么是冲抵而不是收入**：钱先垫出去、再收回来，中间没有新增财富。记成收入会让
  「收入」虚增、支出却不减——两栏同时失真，只有结余碰巧正确。判别口诀：
  **这笔钱事先花出去过吗？花过 = 冲抵，没花过 = 收入（补贴）**。
- 所以收入树里**没有「报销」大类**，只有「补贴」（出差补贴 / 餐补 / 其他补贴）。
  补贴没有原单可挂，是公司白给的钱，记收入；报销有原单，走冲抵。
- 包干补贴（按天给钱、吃住自理）两笔都记：消费照常记支出，补贴记收入，互不冲抵。

**分类饼图下面那句算式（2026-10-30）**

```
分类合计 − 冲抵后为负的分类 − 无主冲抵 = 支出
```

饼图只画**正数**分类（`HAVING SUM(net) > 0`），无主冲抵又没挂到任何分类，所以
「图里各项加起来」天生比「支出」多。以前只画饼不写字，看图的人怎么加都对不上，只会怀疑算错了。
现在 `_api_stats` 额外下发 `cat_total`（饼图各项之和）与 `cat_negative`（被冲成负数、没进图的分类合计），
前端用它们摆一道能当场验算的等式；两个差额都是 0 时（绝大多数月份）只显示「分类合计 X。」，不长篇大论。
- 「归属月」意味着：**10 月买、11 月退/报，改的是 10 月的数字**。已接受这个代价（避免出现"负数支出月"）。
- 分类、归属、共同支出全部按**净额**算；全额冲抵完的消费在分类里净 0、自然消失。
- `by_category` 用 `UNION ALL (支出) + (−分配额)` 求净额，`HAVING SUM(net) > 0` 过滤归零项；
  抵扣项来自 `offset_links` 而不是冲抵记录本身，所以跨分类的一次报销也能减到该减的分类上。
- `by_owner` 同理，冲抵按**原单归属**抵扣（老婆操作退款，钱还是从老公那笔扣）。

### 6.2 两类时间口径

| 字段 | 口径 | 说明 |
|---|---|---|
| `expense` / `expense_gross` / `refund_offset` / `refund_orphan` / `income` / `shared` / `reimb_done` / `by_category` / `by_owner` | **按所选月份** | 传 `month` 参数 |
| `pending` / `pending_cnt` / `voucher` / `voucher_cnt` | **跨月累计** | 垫付和券天然跨月，不按月份过滤；净值统计，`≤0` 的排除 |

### 6.3 结余

前端算：`结余 = 收入 − 净支出`。没有退款时就是 `收入 − 支出`。

**借款不参与**：借出/借入都不进 `expense` / `income`，所以结余看不到它们。这是有意的——借款不是消费也不是收入。代价是结余和银行卡余额会对不上（借出/收回的那天）。

## 7. 筛选 / 搜索 / 排序

`GET /api/tx` 支持 10 个筛选条件（全部 AND）+ 1 个排序键：

| 参数 | 取值 | 说明 |
|---|---|---|
| `month` | `YYYY-MM` | 空则全部月份 |
| `start` / `end` | `YYYY-MM-DD` | **闭区间，含首尾两天**；格式非法直接忽略。与 `month` 同时给时是交集（前端只会给一个） |
| `owner` | 用户 id | 脏值忽略 |
| `direction` | `expense` / `income` / `refund` | |
| `mark` | 同上六个键，**逗号可多选** | **要**这些标记：多个之间是「或」；未知键静默丢弃 |
| `exclude` | 同上六个键，**逗号可多选** | **不要**这些标记：多个之间也是「或」，整体取反（`NOT (...)`）。与 `mark` 正交，可同时给 |
| `cat_parent` | 大类名 | |
| `q` | 关键词 | **空格分隔多个词，词之间 AND**，每个词在「备注 / 子类 / 大类 / 支出人姓名」任一命中即可；词是纯数字时额外按**金额精确匹配**（`25` → 25.00 元），**原额或净额命中都算**（2026-11-02） |
| `min_cents` / `max_cents` | 整数分 | 金额区间，**按原额**（`t.amount_cents`），脏值忽略。刻意不跟显示口径走：用它的场景是「找那笔花了一千多的」 |
| `sort` | `date_desc`（默认）/ `date_asc` / `amount_desc` / `amount_asc` | 只做键名白名单映射，见下。两个 `amount_*` 按**有符号净额**排（2026-11-02） |

**排序为什么用白名单**：`sort` 是唯一会进入 `ORDER BY` 的参数，任何直接拼接都是注入面。
`server.py` 里 `TX_ORDERS` 是一张键 → 排序片段的表，白名单外的值（包括 `;DROP TABLE`）静默回落到
`date_desc`，永远拼不进 SQL。金额排序额外带 `tx_date DESC, t.id DESC` 兜底，同额记录的先后才稳定。

**金额排序用的是 `NET_OUT_SQL` 这个 SQL 片段**（2026-11-02）：`CASE WHEN t.direction='expense'
THEN t.amount_cents - (SELECT COALESCE(SUM(...)) FROM offset_links WHERE parent_id=t.id) ELSE -t.amount_cents END`。
三个用途共用同一份字符串：列表排序、金额搜索、导出 CSV 的净额列——**改口径只改这一处**。
它按 `parent_id` 走相关子查询，`offset_links` 上有 `idx_off_links_parent`，2000 行量级仍是毫秒级；
不要为了「省一次子查询」改成 JOIN 后重算，那会让列表和 `summary` 聚合（同一段 `where`、没有 JOIN）走向两套。
排序与筛选正交：`where` 负责命中集合，`order` 只负责顺序，两者不互相覆盖。

响应 `summary{count, expense(毛额), income, refund}` 与筛选条件同步聚合；`items` 每行额外带 `refunded_cents / refund_count / remain_cents / parent_date / parent_category / parent_amount`，退款行带原单信息用于显示「冲抵 MM-DD 分类」。

**关键词的人名为什么用子查询**：`t.owner_id IN (SELECT id FROM users WHERE display_name LIKE ?)`。
主查询和 `summary` 聚合共用同一段 `where`，而聚合查询没有 `JOIN users`——写成 `u.display_name` 会让
聚合那句直接报「no such column」，整个请求变成错误 JSON（前端表现为读 `items` 报 KeyError）。

上限 `LIMIT 500`。`summary.count` 是 `COUNT(*)`，**不受 LIMIT 影响**，所以前端能用
`count > items.length` 判断「结果被截断」并提示用户缩小范围——静默截断最坑，用户会以为真的只有这些。

### 7.1 前端的时间模型

时间维度只能有一个来源，否则「顶部写着 10 月、列表却是跨年结果」会让人完全分不清：

| `state.filter.scope` | 时间取自 | 顶部显示 |
|---|---|---|
| `month`（默认） | 顶部月份框 `state.month`（为空＝全部月份） | 月份框，或「全部月份 · 按月查看」按钮 |
| `range` | `start` / `end` | 胶囊 `近12月 ✕`（命中预设说名字）/ `24-08-15 ~ 26-11-03 ✕`（自定义跨年）/ `09-01 ~ 10-27 ✕`（自定义同年），点它清除区间回到月份 |
| `all` | 不限 | 同 `month` + 空月份 |

筛选面板里的日期控件就是这三态的 UI：`跟随月份 / 近30天 / 近3月 / 近12月 / 今年 / 全部 / 自定义`。
默认是「跟随月份」，所以**不碰日期就完全等于原来的单月筛选**；一旦在关键词框里打字，会自动切到
「近12月」（胶囊同步高亮，看得见），因为搜索的意图通常是「我记得大概有这笔，但不确定哪个月」。
用户自己选过区间就不会再被自动改。

**「近 N 月」＝含本月在内的 N 个自然月**（2026-11-03 修正）：起点是 N−1 个月前的 1 号。
以前写 `monthsAgo(12)`，从 11 月往前推 12 个月落在去年 11-01，实际覆盖 13 个月——标签说 12 却给了 13，
用户没法拿它对账。`近30天` 仍是滚动窗口（`daysAgo(29)`～今天，含首尾正好 30 天）。

**区间文案必须带够年份**（2026-11-03 用户反馈「近12月无效」的真因）：
原先前端统一 `slice(5)` 砍掉年份，12 个月的范围显示成 `11-01 ~ 11-03`，和「本月 1–3 号」长得一模一样，
看起来就是「筛选没生效」。现在分两个用途两套规则：

| 位置 | 规则 | 例 |
|---|---|---|
| 顶部胶囊 | 命中预设就说**预设名**（用户刚点的那个词，一眼确认生效）；自定义同年只写月日，跨年用两位年份 | `近12月 ✕` / `24-08-15 ~ 26-11-03 ✕` |
| 条件行 | 一律**完整日期**，跨年两端都带四位年份；命中预设再把名字前置 | `条件：日期 近12月 · 2025-12-01 ~ 2026-11-03` |

胶囊文字超宽时省略号截断（`.rc-t`），✕ 单独一个 span 不会被截掉；完整的区间在 `title` 与条件行里。

「重置」（面板内）和「清除全部」（顶部条件胶囊）都会把条件、时间、**排序**一起复位到默认。

### 8.1 错误码（2026-10-30，前端按码分支）

错误体固定 `{"error": "给人看的中文", "code": "给机器认的标识"}`，个别还带明细（如分类保存的 `preview`）。
**前端只认 `code`，不匹配中文文案**——文案随时会改，码才是契约。

| code | 什么时候 | 文案要点 |
|---|---|---|
| `bad_body` | 请求体不是 JSON 对象（数组/字符串/坏 JSON），或字段类型根本没法解析 | 「请求体不是合法的 JSON 对象」 |
| `date_required` | 改账时把日期清空（建账空日期=今天，是另一回事） | 「日期不能为空」 |
| `date_invalid` | 日期不是 `YYYY-MM-DD` 或超出 2000–2100 | 「日期格式应为 YYYY-MM-DD」 |
| `amount_invalid` | 金额 ≤0、>100 万、带字母、浮点、布尔 | 「金额不能超过 100 万元」等 |
| `amount_below_offset` | 支出改到低于已冲抵额 | 「这笔已冲抵 X 元，金额不能低于它」 |
| `direction_has_offsets` | 有冲抵记录的支出要改收支方向 | 「先把冲抵记录删掉再改收支方向」 |
| `category_invalid` | 分类不在当前配置树里 / 收支方向非法 | 「分类不在允许范围内」 |
| `category_has_history` | 删除一个还有历史账单的分类 | 点名哪几个分类、各有几笔 |
| `need_confirm` | 这次保存会改写历史账单，但没带 `confirm:true` | 「会改写 N 笔历史账单」+ 计划明细 |
| `reimburse_requires_record` | 手填/手点「已报销」但没有到账记录 | 「请记一笔到账」 |
| `duplicate` | **不是错误**：同 `client_token` 重复提交，返回 200 + `duplicate:true` | 照常显示「已记上」，别当失败重录 |

实现：`FieldError(ValueError)` 自带 `code`，`parse_tx_date` / `parse_cents` 抛它；
调用方 `except ValueError` 时用 `getattr(e, "code", 默认码)` 取，不再硬编。
**异常原文（`int() argument…`、`time data … does not match format`、`KeyError`）一律只进服务端日志，不进响应体。**

### 9.1 管理员在线维护（设置页 · 分类管理）

**界面形态（2026-10-29 重做）**：一屏只看一棵树——顶部「支出 / 收入 / 退款」三个胶囊（带大类数量），
下面是紧凑列表（每行 46px：色点 + 名字 + 「N 项 · 本月 N 笔」+ 箭头），**点开哪行才就地展开**名称、配色、子类、删除。
以前每个大类永远处于编辑态（无边框名字框 + 10 个色块常驻），16 个大类铺两千多像素，一屏只看得见两个半。

| 能力 | 规则 |
|---|---|
| 权限 | 仅 `is_admin`；普通账号经 `/api/meta` 只读消费 |

| 用量 | 行尾「N 项 · 本月 N 笔」来自 `GET /api/categories/config` 的 `usage{方向:{大类:{total,month}}}`；删除按钮上写「N 笔账在用」（**全量**，不是本月），删之前就知道影响面 |
| 删除 | 两下才真删（第一下把后果摊开，不用系统弹窗）；级联（一级连全部子类）；**有历史账单的分类一律删不掉**（2026-10-30 起，Q-01），只能改名；零笔的空分类可直接删。删空分类后浮条上「放弃」可整体撤回 |
| 未保存提示 | 底部浮动条「N 处未保存 · 放弃 / 保存」，只统计真正改动的大类（改名算 1 处，不是「删一个 + 加一个」算 2 处）；切走页面前 `confirm` 拦一次 |
| **排序（2026-11-03）** | **长按大类行或子类胶囊拖动**，松手落到虚线占位处；顺序就是 `/api/meta` 下发的键序，也就是记账页选择器、筛选大类胶囊的先后。纯换序不算「会改写历史」，保存时不会再弹确认 |
| 改名（子类） | 同父级下消失/新增恰好各 1 个 → 视为改名，**全链条 UPDATE 历史账单**（含冲抵记录的分类副本），统计立即合并；否则视为删除+新增 |
| 改名（一级） | 旧名的子类至少 2 个仍在新名里、且重合度 ≥0.6 才算改名，全链条 UPDATE；否则按「删除 + 新增」处理。只按「交集最大」配对会把「删『餐饮』+ 建『外卖』」误判成改名（两边都有个「其他」），历史被静默改写 |
| 预览与确认 | `POST` 带 `preview:true` 只返回计划（改哪些、影响几笔、哪些会被拦），不写库；会改写历史的保存不带 `confirm:true` 一律 400 `need_confirm` 并回传同一份计划 |
| 保存时的三岔路（前端，2026-10-30） | 点保存先发 `preview:true`：① 计划里有 `blocked` → **弹出提示直接停**，一个字都不写（「这些分类下还有历史账单，不能直接删：…」并给下一步）；② `affected_total>0` → 确认框列出前 3 处改名与各自笔数（「改名会改写 N 笔历史账单，只换分类名，金额和日期都不动」），取消即**零写请求**，确定才带 `confirm:true` 重发；③ 都是 0 → 直接存，不多一次弹窗。落库时服务端按当时的库**重算**一遍计划，上面的 preview 只用来问人，不当提交依据 |
| 双重查重 | 新增名不能撞「历史账单里已有但不在新配置里」的名字，否则两批账会被文本替换强行合并；报错带具体笔数 |
| 日志 | `category_log` 表滚动留 200 条；记时间/操作/旧名→新名/**改名连带笔数**；设置页「分类修改日志」卡片仅管理员可见 |
| 事务 | 配置 + 改名 UPDATE + 日志同一 `with db()` 事务，响应在事务外发 |

两条前端铁律（改这块之前先看）：

1. **click 里可以整块重绘，change（失焦/回车）里只能局部打补丁**。失焦先于点击发生，`change` 里重绘会把用户正要点的元素换掉，那一下点击就丢了——表现是「改完名字点下一行，第一下没反应」。
2. **子类的 × 走 `pointerdown` 而不是 `click`**，并且要 `preventDefault()`。输入框一失焦就会触发 `change` 把这一小段 DOM 换掉，等 `click` 落到时按钮已经不是原来那个元素了。
3. **拖完松手那一下 `click` 要吞掉**（`catClickBlock` 时间戳，400ms 内不响应点击），否则拖完一行会顺手把那一行展开/收起。

**拖动排序为什么这么写（2026-11-03）**：不用 HTML5 drag & drop（手机上根本不触发），也不用 `mousedown/mousemove`（手指按住时页面本来就在滚）。
用的是 Pointer Events + **320ms 长按判定**：按下后不动够久才进入拖动，中途位移超过 8px 就当作滚动、整个撤掉；进入拖动后才在 `document` 上挂非 passive 的
`touchmove` 拦默认行为——给元素直接设 `touch-action:none` 会把这一块的普通滚动也一起废掉。鼠标没有「滚页面」这回事，所以**鼠标一拖就进入拖动**，不必等长按。

落点靠 `document.elementFromPoint`：拖动中的元素是 `position:fixed` + `pointer-events:none`，所以命中的是它底下的兄弟项（忘了 `pointer-events:none` 就永远只命中自己，表现为「拖不动」）。
松手时**从 DOM 顺序反推数据顺序**（占位块在哪、被拖的那项就在哪），不自己算索引——算索引要额外处理「自己被排除」的偏移，看着 DOM 更不容易错。

| 数据怎么落 | 规则 |
|---|---|
| 大类 | 只重建键序（`{...}` 按新顺序重新拼），节点对象整体搬过去，色位与子类原样不动 |
| 子类 | 只重排 `subs` 数组；跨大类拖动不允许（那是改分类，不是排序），只在展开的那个大类里排 |
| 服务端 | **零改动**：`_validate_category_config` 与 `json.dumps` 都保持 dict 插入序，纯换序的 `preview` 返回 `affected_total=0`，所以不会弹确认 |
| 未保存计数 | 大类「键集合相同但先后不同」算 1 处；子类比对用的是 `join`，本身带顺序，天然能感知换序 |

接口：`GET/POST /api/categories/config`（管理员，GET 带 `usage`）、`GET /api/categories/logs`（管理员）。

> 注意：**挂着的退款，分类继承原单**（可能落在支出树里，如「餐饮/早餐」）。所以校验分类时必须先看 `parent_id`，不能一律用退款树校验。解除冲抵回落到**退款树配置的第一个大类第一个子类**（分类可配置后不能写死「其他退款」）。

## 10. 配色与视觉规范

| 对象 | 规则 | 实现 |
|---|---|---|
| 账号 | 按 `user.id` 排序取色，**与显示顺序无关**（否则换人登录颜色就互换） | `OWNER_PALETTE` + `ownerColor(id)` |

### 10.1 手机端适配（只有一套布局）

没有「手机版 / PC 版」两套页面。同一份 HTML 靠 `max-width` 与弹性布局自适应，所以桌面浏览器里看到的就是拉宽的同一版，不是另一套界面。

| 关注点 | 做法 | 原因 |
|---|---|---|
| 视口 | `width=device-width, initial-scale=1, viewport-fit=cover` | 缺 `viewport-fit` 时 iOS 刘海区会留黑边 |
| **输入框字号** | 所有 `input/select/textarea` **不低于 16px** | **iOS Safari 的硬规则**：聚焦字号 <16px 的输入框会自动把整页放大，且按站点记住缩放级别。表现就是「点开页面大了一点、要双指缩小」——本项目的 `body` 是 15px，`font:inherit` 会把输入框一并带到 15px，必须单独覆盖。`#amount` 的 44px、`.alloc` 的 16px 都是同一原因 |
| 横向溢出 | `body{overflow-x:hidden}` | 任何一处超宽都会让 iOS 触发 shrink-to-fit 缩放；这是兜底，不替代修布局 |
| 文字缩放 | `-webkit-text-size-adjust:100%` | 防止横屏 / 部分机型自动放大正文 |
| 安全区 | 底栏 `padding-bottom:env(safe-area-inset-bottom)`，`body` 的底部内边距同样计入 | 全屏模式下不被 Home 条压住 |
| 主屏形态 | `apple-mobile-web-app-capable` + `manifest(display:standalone)` | 从桌面图标打开时**没有 Safari 地址栏和工具栏**，可视区多出约 100px；不加就只能算一个书签，顶部永远被工具栏吃掉一截 |

**图标链路（踩过的坑）**：iOS 的桌面书签**只认真实 URL 上的 PNG**——`data:` URI 的图标和 SVG 版 favicon 它都不吃，拿不到就退化成「黑底 + 标题首字」的默认图（本项目表现为黑底「家」字）。所以：

1. `<link rel="icon" type="image/png">` 必须排在 SVG **前面**，且指向真实文件（`/apple-touch-icon.png`）；
2. 图标满幅不透明、无 alpha（iOS 自己按 squircle 裁圆角，留透明边会露黑底）；
3. 换图标后光刷新页面无效，**必须删掉桌面图标重新添加**——iOS 会缓存旧图标。

## 11. 边界与已知限制

| 项 | 现状 | 影响 |
|---|---|---|
| 单次金额上限 | 1,000,000 元 | 够用 |
| 列表上限 | 500 条/次 | 家庭场景足够；如需更多要加分页。**导出不受此限**（整份拿走） |
| 导出格式 | 只有 CSV，没有 Excel（xlsx）/ PDF / 账单图片 | 导出的目的就是「能拿出去算/能换系统」，CSV 各家都认；要 xlsx 得引第三方库，与「纯标准库」冲突 |
| 导出范围 | 一次导**当前筛选**的结果，不能一次导出「所有月份 + 全部明细 + 统计页」 | 想全量就先在筛选里放开月份，再点导出 |
| 备注长度 | 截断 100 字 | — |
| 月份口径 | 归属月，跨月退款会**回改历史月份** | 已确认接受 |
| 待报销/待用券 | 跨月累计，不分月 | 设计如此 |
| 无主退款月净支出 | 可能为负 | 语义正确（本月净流入），UI 会显示负号 |
| 删除不可撤销 | 无回收站，但**每次删除都留完整快照**（见 §11.1），可按它手工恢复 | 删原单时退款转无主，有二次确认 |
| 并发 | SQLite + WAL，单机两人够用 | 不做多租户 |
| 改账校验 | 与建账同一套解析函数（日期/金额/上限），见 §15 | 改账不再比建账松 |
| 时区 | 固定 UTC+8 | — |
| 会话 | 30 天，cookie 带 Secure | 必须走 HTTPS |
| **无记录级权限** | 登录后**所有成员都能改、能删任何一笔**（包括对方记的），不做「只能动自己的」 | **这是有意的**：一本家庭账，成员之间的权利本来就对等。系统留下「谁最后改的、谁删的」够事后对质（§11.1），但不拦人 |
| 无并发编辑检测 | 两人同时改同一笔，后保存的覆盖前面的，不提示「这条已被改动」 | 两人一本账，撞车概率极低；真要防得加版本号 + 前端提示，暂不做 |

### 11.1 审计：谁改的、谁删的

家庭 / 小团队的账，出了「这笔记怎么变了」得能查。留了三样东西，都不占界面空间：

| 留了什么 | 存在哪 | 怎么用 |
|---|---|---|
| 最后改的人 | `transactions.updated_by`（启动时自动加列，历史行留空） | 改一笔就更新成**后动手的那个人**；`/api/tx` 返回里带这个字段 |
| 删除快照 | `audit_log` 表：时间、操作人、表名、记录 id、**整行 JSON + 那条冲抵的分配明细** | 删错了照着 JSON 手工重建。分配明细必须一起存——那几行会被 `ON DELETE CASCADE` 清掉，不存就只剩「某天删了一条冲抵」，等于没记 |
| 访问日志 | 进程 stdout（systemd 里就是 `journalctl -u ledger`） | 只记**写操作（POST/PATCH/DELETE）和 ≥400**，一行：`时间 方法 路径 状态 user=… 耗时`。正常浏览不记，否则一天几百行把有用的淹掉 |

看删除记录：

```bash
ssh your-server "sqlite3 -readonly /opt/ledger/data/ledger.db \
  'SELECT ts,username,kind,tx_id,substr(before_json,1,120) FROM audit_log ORDER BY id DESC LIMIT 20'"
```

**不记「每一次改动」**，只记最后一次（`updated_by`）。家庭账本不是审计系统，留一个可以问的人就够；
再加张改动历史表，收益很小、每次保存多写一行，不值。真要追溯某笔的改动过程，靠访问日志里那几行写操作反推。

金额、类目这些**约束性的东西另说**：它们是数据库层强制的（§13.2 的 CHECK），不是靠审计兜底。

### 13.2 表结构版本与自动迁移（2026-10-30 起）

表结构升级不再是「往 settings 塞一个 `migr_xxx` 标记」，改成一个数字：`settings.schema_version`。
启动时自动按序升到 `server.py` 里的 `SCHEMA_VERSION`，日志打印 `[schema] 已升到 vN：…`。

当前版本：

| 版本 | 内容 |
|---|---|
| v1 | `transactions` / `offset_links` 加 CHECK 约束（方向三值、金额>0、日期严格 `YYYY-MM-DD`、分配不重复不超自身） |
| v2 | `transactions.updated_by` + `audit_log` 删除审计表 |

```bash
ssh your-server "sqlite3 -readonly /opt/ledger/data/ledger.db \"select value from settings where key='schema_version'\""
```

**三条要知道的行为**：

1. **有脏数据就不升级**——启动时先检查，发现不满足约束的行就跳过、打一行 `[schema] 跳过 v1：…`，
   表结构保持原样、**服务照常可用**。此时按提示跑体检脚本修干净再重启即可。
   硬上会让进程起不来，账一笔记不了，那比「少一层约束」严重得多。
2. **迁移是一个事务，失败整体回滚**，不会留半截的表。要关外键（`PRAGMA foreign_keys=OFF`）才做，
   否则 `DROP TABLE transactions` 会顺着 `ON DELETE CASCADE` 把 `offset_links` 清空。
3. **升级前一定先备份**：`ledger-backup.sh` 然后重启。回滚 = 换回旧代码 + 用备份包的数据。

改表结构的规矩写在 `server.py` 顶部常量旁边：表定义只有 `TRANSACTIONS_DDL` 一份，
索引清单只有 `TRANSACTIONS_INDEXES` 一份，新库和重建走同一套。**别再往 `init_db` 里抄第二份。**

**数据与代码分离**：代码进 Git，数据（`data/`、`TOKEN`、`gatus/config.yaml`、Caddyfile）永不入库，换机器按 `服务器重建手册.md` 手工补。

## 15. 改一条账的硬规则（PATCH，2026-10-30）

建账（`POST /api/tx`）一直有完整校验，改账（`PATCH /api/tx/{id}`）曾经几乎没有——
2026-10-29 审查出的 7 条 P0/P1，**6 条只需要一条 PATCH 请求**就能触发。现在两个入口共用同一批
解析函数（`parse_tx_date` / `parse_cents` / `parse_opt_int`），并且都带 `code` 供前端分支。

| 规则 | 口头说法 | code |
|---|---|---|
| 日期必须是 `YYYY-MM-DD` 且在 2000–2100 之间 | 「日期格式应为 YYYY-MM-DD」 | `date_invalid` |
| 金额必须 > 0 且 ≤ 100 万元（与建账同一上限） | 「金额不能超过 100 万元」 | `amount_invalid` |
| 支出的金额**不得低于已冲抵额** | 「这笔已冲抵 150 元，金额不能低于它」 | `amount_below_offset` |
| 有退款/报销冲抵的支出**不许改收支方向** | 「先把冲抵记录删掉再改收支方向」 | `direction_has_offsets` |
| 摊在多笔上的冲抵不许在这里改金额 | 「请到「冲抵分配」里改金额」 | — |
| 冲抵记录的**归属、分类强制跟随原单** | 改了不报错，但不生效 | — |
| 「已报销」只能由到账记录置位 | 「不能手动打开：请记一笔到账，系统会自动标记并冲减支出」 | `reimburse_requires_record` |
| 非支出记录的 5 个标记（含已报销）一律清 0 | 不报错，直接清 | — |
| 请求体必须是 JSON 对象 | 数组/字符串当空体处理，不 RST 连接 | — |

**为什么金额不能低于已冲抵额**：支出 200 已退 150，再把金额改成 100，净支出就是 −50；
分类饼图那一块直接消失，而且没有任何代码会再纠正它——只能等月底对账时肉眼发现。

**为什么改方向要拦**：冲抵记录挂在原单上，方向一改，那 20 元既不在「本月冲抵」也不在
「无主冲抵」里，钱凭空消失且界面一声不吭。

**为什么归属不许改**：冲抵记录是原单的影子。允许改会造出「明细算在 A 头上、统计按 B 抵扣」
两套账——这类不一致最难查，因为两个页面的数字单独看都对。

**为什么这些是「静默清 0 / 静默忽略」而不是报错**：前端保存时整包提交表单字段（旧版 PWA
缓存也会），报错会让「只改个备注」这种操作莫名失败。真正需要拦的（会破坏金额守恒的）才返回 400。

接口侧还有一层兜底：`do_GET/do_POST/do_PATCH/do_DELETE` 都套了 `_safe()`，
未预期异常一律变成 500 + 完整 traceback 进 `journalctl`，不再让客户端拿到「连接重置」——
后者无法区分「服务器崩了」和「网断了」，也丢掉了排查线索。
